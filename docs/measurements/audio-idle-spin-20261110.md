# 何も鳴らしていない間の CPU：鳴っていない stream を休ませた後の再計測

前の計測は [audio-core-load-20261110.md](audio-core-load-20261110.md)。k は「実データの曲（`untitled.mid`）の track を k 倍に複製した SMF」の倍率で、plugin instance は 6k 個、曲の part は 4k 個。
設計は [ADR 0022](../adr/0022-parallel-part-rendering.md)（鳴っていない stream では spin も plugin・effect・master effect の処理も止める）。

## 結論

| 条件 | 目標 | 結果 | 合否 |
|---|---|---|---|
| GUI 有り k=1、何も鳴らしていない 6 秒の本体 CPU（12 論理コアを 100%） | 13.5 + 2 = 15.5% 以下 | **7.1 / 9.1 / 9.2 %**（休ませる前は 29.0〜29.6%） | 合格 |
| GUI 有り k=4、Space 再生の定常（開始 1.5 秒より後）の途切れ | 3 回とも 0 件 | **0 件**（6 回とも） | 合格 |
| GUI 無し k=4（`realtime_song_probe`）の定常の途切れ | 3 回とも 0 件 | **0 / 0 / 0 件** | 合格 |
| k=1 の定常の途切れ（GUI 有り Space・GUI 無し） | 0 件のまま | **0 件**（各 3 回） | 合格 |
| 曲の stream が休んだ後の Space の鳴り始め（1.5 秒以内）の途切れ | 増やさない（前の計測は 0 件） | **0 件**（k=1 3 回・k=4 6 回） | 合格 |
| keyboard の stream が休んだ後の打鍵の鳴り始め（1.5 秒以内）の途切れ | 増やさない | **0 件**（k=1・k=4 で各 3 打鍵、全打鍵の前に休んでいた） | 合格 |

- 何も鳴らしていない間に 0.8 core を超える thread は 1 本（0.82〜0.98 core）。休ませる前は 3 本（spin 2 本 + この 1 本）。残る 1 本は UI thread とみる `[未検証: thread 名では確かめていない]`。
- k=4 の GUI 有りでは、何も鳴らしていない間の本体 CPU が 8.7〜9.2%（6 回）。同じ作業ツリーで休む判定を常に偽にした build では 42.6 / 43.3 / 43.4%（0.8 core を超える thread 3 本）。

- Space はどの回も 1 回目で曲の再生になった（Space の後に `parts=4k` の `[audio-command]`）。どの回も Space の時点で曲の stream は休んでいた。
- この曲は plugin parameter の automation を持つので、Space は休んでいた stream を再開せず、新しい stream（stream 3）を開く（`src/play/audition.rs:182` の `voice.automated()`）。よって GUI の Space の鳴り始めは「何も処理していない状態から新しい stream を開く」場合で、「休んでいた stream の再開」は上の `realtime_live_probe` で測った。どちらも同じ `Mixer` を通る。
- keyboard の途切れ（k=4 の 4 / 6 回、約 9.5〜10ms）は、どれも keyboard の stream を開いた 1.0 秒後の 1 件（休む前、自動再生の曲の余韻を処理している最中に開く）。休む判定を常に偽にした build でも k=4 で 1 / 9.1、1 / 9.4、0 件と同じ形で出たので、休ませる変更で増えたものではない。前の計測はこの区間を数えていなかった。
- 計測後に実データの `untitled.mid` の hash が変わっていないことを毎回確かめた。

## 測り方

- GUI 無し: repo の ignored テスト `realtime_song_probe`（15 秒）と `realtime_live_probe` に `AUDIO_PROBE_SMF` で生成した SMF を渡した。判定はその pid の、実行を始めた時刻より後の `error.log` の行。part 数は `[audio-command]` の `parts=`。
- GUI 有り: `%LOCALAPPDATA%\cat-smf-editor` を temp へ複製し（`backup` と log を除く）、複製の `startup.json` / `status.json` を生成した SMF に向け、本体に `LOCALAPPDATA` / `TEMP` / `TMP` を temp に向けて起動した。両 stream の `[audio-rest]` を待ってから 1 秒後に 6 秒、process と thread ごとの CPU 時間の差分を取った。その後 `AttachThreadInput` で前面に出し、`PostMessageW` で Space を送って 15 秒を見た。終了は `WM_CLOSE`。
- 負荷を上げた SMF の作り方は前の計測と同じ（track を k 倍に複製し、pattern / pattern-container の id を付け替え、Song の配置に lane と項目を足す）。k=1 で作ると元と同じ bytes になることを確かめた。
- 比較用の build は、休む判定（`Rest::resting`）を一時的に常に偽にして作り、計測後に元へ戻した。
- 計測環境: Windows 11、i7-8700K（6 core 12 thread）、電源「バランス」、既定デバイス 48kHz、外部負荷なし。
- 表を作った python script と生成した SMF は使い捨てで、repo には残していない。
