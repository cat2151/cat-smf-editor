# 音源を多く使う曲の音途切れ：修正後の再計測

修正前の計測と条件の定義は [audio-dropout-gui-vs-core-20261110.md](audio-dropout-gui-vs-core-20261110.md)。
k は「実データの曲（`untitled.mid`）の track を k 倍に複製した SMF」の倍率で、plugin instance は 6k 個、再生 part は 4k 個。

## 結論

| k=4、GUI 有り、Space 再生の定常の途切れ | 3 回とも 0 件 | 36 / 29 / 24 件 | **0 / 0 / 0 件** | 合格 |
| k=4、GUI 無し（probe）の定常の途切れ | 3 回とも 0 件 | 25 / 34 / 32 件 | **0 / 0 / 0 件** | 合格 |

| Virtual MIDI keyboard の stream（stream 2）の途切れ（k=4、Space 再生中） | - | 42 / 27 / 5 件 | 0 / 0 / 0 件 | - |

k=1〜4 の全 24 回（GUI 無し 12・GUI 有り 12）で、定常の途切れは 0 件。開始 1.5 秒以内の 1 件・約 6ms（修正前から出ていた形）は、GUI 無し k=4 の 2 回と GUI 有りの起動時の自動再生 k=4 の 2 回に残る。

## 直したこと

- 1 回の audio callback の中で、part（1 track の楽器と track effect）どうしを worker thread で並列に処理する。同じ part の楽器と effect は 1 thread で順に処理し、mix・master は全 part の後に直列。参加 thread は part 数と論理 CPU 数の半分の小さい方（この機械では最大 6）。設計は [ADR 0022](../adr/0022-parallel-part-rendering.md)。
- 各 part は自分の note・timeline・automation の境界だけでブロックを区切る。修正前は automation を持つ 1 part の 64 frame 格子で全 part が約 8 回に分割されて plugin を呼んでいた。
- 実時間の stream の worker と callback の thread を `TIME_CRITICAL` にする。

### 代償：何も鳴らしていない間も CPU を使う

worker の 1 本は次のブロックを spin で待つ（全 worker が休むと plugin が約 2.5 倍遅く走ったため。ADR 0022）。stream が開いている間、stream ごとに 1 core 分を使い続ける。GUI 有りでは曲の stream と Virtual MIDI keyboard の stream の 2 本が開いているので 2 core 分。

| 計測 | 本体の CPU（12 論理コアを 100%） | 1 core 以上を使い続ける thread |
|---|---|---|
| k=1、曲の再生が終わって何も鳴らしていない 6 秒（修正後、3 回） | 29.6 / 29.0 / 29.1 % | 2 本（各 1.01〜1.02 core） |
| 同上、spin を一時的に止めた build（1 回） | 13.5 % | なし |
| k=4、何も鳴らしていない 6 秒（修正後、3 回） | 44.0 / 43.9 / 44.4 % | 2 本 + UI thread |

差の約 15 ポイント（12 論理コアで約 1.9 core）が spin の分。電力・発熱・ファンの音に効く。

### fps は修正前の報告より低いが、今回の修正のせいではない

k=2 の fps は修正前の報告で 57.9〜59.1、今回 43.3〜44.0。k=3 も 42.4〜45.7 から 29.7〜30.5 に下がった。UI thread の CPU は 90〜94% で、UI thread が 1 core を使い切っている。

| 同じ作業ツリーで k=2 を 1 回 | fps | UI thread CPU % | 本体 CPU % |
|---|---|---|---|
| 修正後（並列・spin あり） | 43.3〜44.0（3 回） | 93.3〜93.4 | 35.6〜36.7 |
| spin を止めた build（並列・全員 park） | 43.8 | 91.3 | 21.4 |
| 参加者 1 の build（直列。spin も helper も無し） | 46.0 | 89.3 | 16.6 |

並列化や spin を外しても fps は戻らないので、低下は audio の修正ではなく、修正前の計測からこの作業ツリーに入った他の変更（画面側）によるものとみる `[未検証: どの変更かは分けていない]`。

## 測り方

- GUI 無し: repo の ignored テスト `realtime_song_probe` を 15 秒。判定は修正前と同じく、その pid の最後の `[audio-command]` 以降の `[audio-dropout]` 行で、開始 1.5 秒以内を onset とした。instance 数は stdout の remidy の `instantiating` 行、part 数は stderr の `parts=` で確かめた。
- GUI 有り: `%LOCALAPPDATA%\cat-smf-editor` を temp へ複製し（`backup` と log を除く）、複製の `startup.json` / `status.json` を生成した SMF に向け、本体に `LOCALAPPDATA` / `TEMP` / `TMP` を temp に向けて起動した。自動再生と Virtual MIDI keyboard の stream が開いた後、何も鳴らさない 6 秒の CPU を取り、前面に出してから Space を送って 15 秒を見た。終了は `WM_CLOSE`。fps・update・UI thread CPU は `CAT_SMF_FRAME_TRACE` の、Space の再生位置が動いている区間。CPU は process と system の CPU 時間の差分。1 core 以上を使い続ける thread は、3 秒間の thread ごとの CPU 時間の差分が 0.8 core を超えるもの。
- 負荷を上げた SMF の作り方は修正前の報告と同じ（track を k 倍に複製し、pattern / pattern-container の id を付け替え、Song の配置に lane を足す）。
- 計測環境: Windows 11、i7-8700K（6 core 12 thread）、電源「バランス」、既定デバイス 48kHz、外部負荷なし。
- 表を作った python script と生成した SMF は使い捨てで、repo には残していない。
