# 音途切れの原因の切り分け：GUI とのスレッド設計か、コアの設計か

## 結論

| 問い | 判定 | 根拠の数値 |
|---|---|---|
| GUI とのスレッド設計（GUI が描画用 lock を握る）が原因か | **当たらない** | `render_lock_misses` は GUI 有り 24 回中 22 回で 0、残り 2 回も 1 件だけで、どちらも起動直後の再生。GUI 無しでも 12 回中 1 回が 1 件（GUI が無いのに出る） |
| GUI に関係ないコアの設計（callback の処理が重い）が原因か | **主因** | GUI 無しで k=2 から 3 回とも定常で途切れる。途切れ付近の callback の最長は中央値 15〜21ms、最大 19〜26ms で、1 回の要求 10ms（480 frame）を超えている |
| 「呼ばれるのが遅れた」型（他プロセスの CPU 占有など） | **通常条件では出ない** | 外部から 12 論理コアを python の busy loop 24 本で飽和させても、再生が定常に入ってからの飽和では 6 回とも 0 件。出たのはストリーム開始時に既に飽和していた回の、開始約 1 秒後の 1 件・6.1〜7.1ms だけ（callback 最長 7.6〜10.1ms） |
| GUI があると悪化するか | **しない（k≤3 ではむしろ少ない）** | k=2: GUI 無し 3 回とも定常 1〜3 件、GUI 有り 6 回とも 0 件。k=3: GUI 無し 12〜27 件、GUI 有り 0〜2 件。k=4 は件数がほぼ同じ（GUI 無し 25〜34、GUI 有り 24〜36） |

k は「実データの曲（`untitled.mid`）の track を k 倍に複製した SMF」の倍率。k=1 で plugin instance 6 個・再生 part 4 個、k 倍でそれぞれ k 倍になる。

## 判定の基準

途切れは `error.log` の `[audio-dropout]` 行（`src/play/audio_diagnostics.rs` の `Dropouts`）で数える。判定の原理は、WASAPI が callback に渡す要求量から「再生済みの量」を積算し、経過時間より遅れた分を無音とみなすもの。callback をわざと 20ms / 40ms 止めた検証で、ループバック録音のずれ（8.0ms×10 / 約 22ms×10）と件数が一致し、15ms 以下の停止では録音・ログとも 0 だった。

| ログの形 | 疑う原因 |
|---|---|
| `[audio-diagnostic]` の `render_lock_misses` > 0 | GUI 側が描画用 lock を握っている（GUI とのスレッド設計） |
| `[audio-dropout]` かつ `slowest_nearby_callback_ms` が 10ms を大きく超える | callback の処理が重い（コアの設計） |
| `[audio-dropout]` かつ callback は速い | 呼ばれるのが遅れた（GUI や plugin の別スレッドの CPU 占有、スレッド優先度、OS） |

列の定義:

- onset: 再生開始の `[audio-command]` 行から 1.5 秒以内に記録された途切れ。定常: それ以降。値は件数 / 無音 ms の合計。
- slowest: `[audio-dropout]` 行の `slowest_nearby_callback_ms` の最大 / 中央値。
- lock: `render_lock_misses` の合計。

計測環境: Windows 11、12 論理コア、既定デバイス 48kHz・バッファ容量 1056 frame、外部負荷なし（下の「外部負荷」の節を除く）。1 条件 15 秒×3 回。

## 原因の判定

### GUI とのスレッド設計: 当たらない

- 描画用 lock を取れずに無音を書いた回数（`render_lock_misses`）は、GUI 有り 24 回で合計 2、どちらも起動時の再生の 1 件。scroll で GUI を忙しくしても増えない。
- GUI 有りの方が途切れは少ない（k=2・3）。GUI が audio callback を妨げている形ではない。

### コアの設計: 主因

- GUI 無しで k=2（instance 12 個）から、定常で途切れる。途切れ付近の callback は 15〜26ms かかっており、10ms の周期に間に合っていない。
- k を上げると定常の件数と無音 ms が増える（GUI 無し k=2: 1〜3 件、k=3: 12〜27 件、k=4: 25〜34 件）。
- GUI 有りの k=3・4 でも Space の再生の slowest は中央値 12〜25ms で、同じ形。

### どちらでもない（未調査のまま残るもの）

| 現象 | 数値 | 候補 |
|---|---|---|
| GUI 無しの方が k=2・3 で途切れが多い | k=3 の定常: GUI 無し 12〜27 件、GUI 有り 0〜2 件 | `[未検証]` probe の main thread（5ms ごとの `pump`）の動き、plugin の内部スレッド、電源・クロック状態。起動直後の 1 回目の再生も GUI の方が少ないので、「2 回目で plugin が温まっている」だけでは説明できない |
| ストリーム開始約 1 秒後の 1 件・約 6〜10ms | GUI 無し k=2 で 3 回とも 1 件・約 6ms、GUI 有り k≥3 の Space で毎回 1 件・約 10ms、外部負荷下 k=1 で 1 件・6.1〜7.1ms | `[未検証]` 開始時の誤検出か、音の出始めより前に入った無音か。clean な録音 6 本ではずれとして見えなかったが、相互相関は最初の 1 秒の音を基準にするので出始めより前は測れない |
| 曲を鳴らしていない stream 2 でも途切れる | k=2: 1 件・約 10ms、k=3: 1〜2 件・約 20ms、k=4: 5〜42 件・116〜1664ms | `[未検証]` 試聴用の voice（`src/play/audition.rs` の `prepare` が全 track の patch を開く）。無音の間も全 instrument を毎ブロック処理しているなら、曲の再生と同時に 2 本分の plugin を回している |
| 録音にだけ出る 77〜126ms のずれ | アプリ側 2 回・対照 1 回 | Windows の音声エンジンかループバック取得の経路。`[未検証]` 耳で聞こえる途切れかは機械では区別できない |
| remidy の `params.flush() on wrong thread!` | GUI 無しで約 20 行、GUI 有りで k ごとに 40k 行 | `[未検証]` 途切れとの関係は調べていない |

## 修正候補（実装はしていない）

| 候補 | 対象 | 期待 | 先に確かめること |
|---|---|---|---|
| track ごとの plugin 処理を複数スレッドへ分ける | コア | 12 コア中 2.5 コア程度しか使っていないので、並列化で 1 ブロックの処理時間を縮められる見込み | `[未検証]` 1 ブロックの中で全 track を 1 スレッドで順に処理しているか。instance ごとの処理時間の内訳 |

## 再現

GUI 無しの 1 回分は repo の ignored テストで再現できる。

```powershell
$env:AUDIO_PROBE_SMF = 'D:\path\to\song.mid'   # AUDIO_PROBE_SECONDS で秒数を変えられる（既定 15）
cargo test --release --bin cat-smf-editor realtime_song_probe -- --ignored --nocapture --test-threads=1
```

結果は `%LOCALAPPDATA%\cat-smf-editor\error.log` の、stderr の `pid=` と同じ pid の `[audio-dropout]` / `[audio-diagnostic]` 行に出る。pid は実行をまたいで再利用されるので、その pid の最後の `[audio-command]` 行以降だけを数える。

負荷を上げた SMF は、元の曲の track を k 倍に複製して作る。複製では pattern / pattern-container の id を付け替え、track 0 の Song 配置に lane を足す（id が重なると再生準備が失敗する）。patch の参照は変えない。

GUI 有りの計測は、`%LOCALAPPDATA%\cat-smf-editor` を temp へ複製し、アプリにだけ `LOCALAPPDATA` / `TEMP` / `TMP` を向けて release build を起動する（実データを書き換えないため）。Space で再生し、fps は `CAT_SMF_FRAME_TRACE` で取る。

表を作った python script は使い捨てで、repo には残していない。比べ直すときは、その時点の SMF 形式と修正の形に合わせて作り直す。
